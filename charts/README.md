## 1. Secret Mapping Mechanism

The chart handles sensitive data like passwords and OAuth client secrets securely without exposing them in plaintext configurations.

### How the `secrets` block works
The `secrets` section maps existing Kubernetes Secrets to environment variables, and then bridges those environment variables into the HOCON configuration file.

#### Step-by-Step Translation:
1. **Environment Variable Injection (`deployment.yaml`):**
   * The Deployment template iterates over the `secrets` list using the index (`$secretIndex`).
   * It calls the `pqs.secretEnvVarName` helper function, which outputs an indexed name like `PQS_SECRET_0`.
   * It creates an environment variable pulling the value from the specified `secretKeyRef` (e.g., pulling the `postgresPassword` key from the `postgres` secret into `PQS_SECRET_0`).

2. **HOCON Substitution (`configMap.yaml`):**
   * The ConfigMap also iterates over the `secrets` list using the same index.
   * For every property listed in `paths` (e.g., `target.postgres.password`), it appends a HOCON variable assignment to `app.conf`.
   * The generated line looks like this:
     ```hocon
     target.postgres.password = ${PQS_SECRET_0}
     ```

#### The Final Result
When PQS reads `/app/app.conf`, it loads the base config, then reads the appended secret paths and resolves them using HOCON's native environment variable substitution (`${VAR}`). This integrates Kubernetes Secret management while avoiding plaintext leaks.

* **Example Values File Configuration:**
  ```yaml
  secrets:
  - paths:
    - target.postgres.password
    secretKeyRef:
      name: postgres
      key: postgresPassword
  - paths:
    - pipeline.oauth.clientSecret
    secretKeyRef:
      name: splice-app-validator-ledger-api-auth
      key: client-secret
  ```

## 2. PQS Configuration & HOCON Generation

The `pqs` section manages the core application configuration for PQS (Scribe). Instead of mapping individual fields directly to command-line arguments, this Helm chart uses a  **JSON to HOCON** bridging mechanism inside the `ConfigMap`.

### How the `pqs` block works
1. **JSON Serialization:** The entire `pqs` block from `values.yaml` is serialized into a raw JSON file called `values.json` within the ConfigMap (`{{ .Values.pqs | toPrettyJson }}`).
2. **HOCON Generation:** The application is booted with `--config=/app/app.conf`. The `app.conf` file is also generated by the ConfigMap and starts with the directive:
   ```hocon
   include required(file("/app/values.json"))
   ```
3. **Mounting:** The `deployment.yaml` mounts the ConfigMap as a volume which allows you to supply any nested configuration structure inside the `pqs:` values block without needing to update the Helm template every time a new configuration parameter is added to the application.

Below are the primary sub-sections of the `pqs` configuration and how to configure them.

### `pqs.pipeline`
* **Description:** Configures the data ingestion pipeline, including the data source type, contract filters, ledger read positions, and OAuth authentication specifics.
* **Example Values File Configuration:**
  ```yaml
  pqs:
    pipeline:
      datasource: TransactionStream
      filter:
        betterWildcard: "true"
        contracts: "*"
        metadata: "*"
        parties: "*"
      ledger:
        start: Latest
        stop: Never
      oauth:
        clientId: splice-oauth-client-id
        issuer: "https://provider.oauth.com/fakeIssuer"
        endpoint: "https://provider.oauth.com/fakeIssuer/token"
        preemptExpiry: PT1M
        scope: daml_ledger_api
        parameters:
          audience: "http://fake.audience.com"
  ```

### `pqs.source`
* **Description:** Defines the connection parameters to the participant node (Ledger API), including host, port, authentication type, and connection keep-alive settings.
* **Example Values File Configuration:**
  ```yaml
  pqs:
    source:
      ledger:
        auth: OAuth
        bufferSize: "128"
        cacheDir: "/tmp/scribe"
        host: participant
        keepAlive:
          time: PT40S
          timeout: PT20S
        port: "5001"
  ```

### `pqs.target`
* **Description:** Configures the destination for the queried data. This defines the PostgreSQL database connection, connection pooling, schema, and encoding preferences.
* **Example Values File Configuration:**
  ```yaml
  pqs:
    target:
      encoding:
        excludeNulls: "false"
        int64AsString: "true"
        numericAsString: "true"
      postgres:
        appName: scribe
        bufferSize: "128"
        database: public
        host: postgres
        keepAlive: "true"
        maxConnections: "16"
        username: "postgres"
        port: "5432"
        schema: pqs
        tls:
          mode: Disable
      schema:
        autoApply: "true"
        baseline: "false"
  ```

### `pqs.retry`
* **Description:** Specifies the retry policies and exponential backoff parameters for handling transient failures in the pipeline.
* **Example Values File Configuration:**
  ```yaml
  pqs:
    retry:
      backoff:
        base: PT1S
        cap: PT1M
        factor: "2.0"
      counter:
        reset: PT10M
  ```

### `pqs.health`
* **Description:** Configures the bind address and port for the application's health check endpoints, which Kubernetes uses for liveness and readiness probes.
* **NOTE:** `address:` has to always be `0.0.0.0` in order for Kubertetes to correctly expose the `livez` endpoint.
* **Example Values File Configuration:**
  ```yaml
  pqs:
    health:
      address: "0.0.0.0"
      port: "8091"
  ```

### `pqs.logger`
* **Description:** Controls the logging behavior of the application, such as log levels and output formats.
* **Example Values File Configuration:**
  ```yaml
  pqs:
    logger:
      format: Plain
      level: Info
      mappings: {}
      pattern: Plain
  ```
